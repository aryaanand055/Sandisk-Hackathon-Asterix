## 2. Structural ground rules

**GR-1 — `run_id` is the join key.** Format `RUN-%06d`, unique per bundle, present
in every file that has a run grain. Never join on anything else.

**GR-2 — One row per run** in `config.csv`, `randomization.csv`, `telemetry.csv`,
`outcomes.csv`. **Many rows per run** in `transactions.csv` and `registers.csv`.

**GR-3 — `transactions.csv` is a window, not a census.** It carries up to 10 logged
transactions per run, while `config.num_transactions` is the programmed total
(up to 4,096). The two are *not* meant to match. Every *failing* transaction is
always in the window, so error rows reconcile exactly (see GR-11).

**GR-4 — Column aliases are real.** Bundle B renames columns on purpose, to prove
the normalizer works:

| Canonical | B's name | File |
|---|---|---|
| `run_id` | `runId` | `config.csv`, `outcomes.csv` |
| `run_id` | `Run_ID` | `transactions.csv` |
| `run_id` | `simulation_id` | `telemetry.csv` |
| `test_name` | `testcase` | `config.csv` |
| `txn_id` | `transaction_id` | `transactions.csv` |
| `status` | `result` | `outcomes.csv` |
| `failure_type` | `failure_class` | `outcomes.csv` |
| `error_code` | `err_code` | `outcomes.csv` |

Bundle A uses canonical names throughout. Each bundle's `MANIFEST.json` carries its
own `column_aliases` map.

**GR-5 — Custom columns must survive.** Non-standard columns are seeded in both
bundles and must be preserved, not dropped: A has `wear_leveling_mode`,
`plane_interleave`, `vendor_cmd_set`; B has `vendor_ip_rev`, `lint_waivers`.

**GR-6 — Absent means absent.** `MANIFEST.json → absent_categories` lists what a
bundle does not ship. C has no randomization, telemetry, log or waveform; D has
only a log; B has no waveform. Those panels must render an explicit unavailable
state, never an imputed or carried-over value.

**GR-7 — Only raw measurements are in the input files.** What is present: config
knobs, seeds and randomized fields, transaction inputs/outputs, protocol signal
values, UVM report lines, assertion events, register accesses, environment
telemetry, PASS/FAIL, `execution_time_ms`, `throughput_mbps`, `sim_cycles`.

What is **never** present, and must be computed by the analytics layer:
latency, failure probability, risk score, failure rate, correlation, feature
importance, SHAP, cluster id, Pareto rank, recommended config, confidence, root
cause. The validator fails the build if any such column appears.

**GR-8 — `uvm.log` is self-sufficient.** Its `[CONFIG]` block embeds the config
knobs *plus* `seed`, `temperature_c`, `voltage_mv`, `power_mode`,
`payload_entropy` and `rand_traffic_pattern`, so legacy single-log mode can still
see the cross-file rule drivers. The grammar is byte-compatible with
`uvm_intel/log_format.py` — the existing parser reads these logs unchanged
(verified: 6,000/6,000 and 4,000/4,000 blocks, 0 malformed).

**GR-9 — Timestamps are real nanoseconds.** `start_time_ns` = `execution_time_ms`
× 1e6, consistent with `sim_cycles` at the configured clock. (This corrects the
old corpus, which used a ×1,000 scale.)

**GR-10 — The same run means the same thing everywhere.** A run's config in
`config.csv` and in the log's `[CONFIG]` block agree; its verdict in
`outcomes.csv` and in the log agree.

## 4. Causal ground truth — Dataset A (NVMe/AXI4)

Baseline failure probability for a clean config is **1.2%**, deliberately below the
2% ceiling the recommender optimizes against, so that constraint is satisfiable.
Failures come from the rules, not from the floor.

| ID | Rule | Source files | Effect | Error tag | Runs | Share | Fail when fired | Base | Lift |
|---|---|---|---|---|---|---|---|---|---|
| A1 | `test_name=Back_To_Back_Program` ∧ `cache_policy=Adaptive` | config | set 0.85 | `FIFO_OVERFLOW` | 339 | 5.7% | 89.4% | 22.3% | **4.01** |
| A2 | `test_mode_enabled=1` | config | +0.35 | *(none)* | 1,669 | 27.8% | 50.2% | 16.8% | 2.98 |
| A3 | `queue_depth≥32` ∧ `ecc_mode=Disabled` | config | +0.32 | `ECC_UNCORRECTABLE` | 245 | 4.1% | 55.1% | 24.9% | 2.22 |
| A4 | `temperature_c>80` ∧ `voltage_mv<1120` | **telemetry** | +0.30 | `RETENTION_FAIL` | 173 | 2.9% | 58.4% | 25.1% | 2.32 |
| A5 | `num_planes=4` ∧ `burst_length=64` ∧ `scrambler_enable=1` | config | set 0.97 | `PROTOCOL_VIOLATION` | 93 | 1.6% | **100%** | 24.9% | 4.01 |
| A6 | `clock_freq_mhz≥1000` ∧ `prefetch_depth>8` | config | +0.28 | `TIMEOUT` | 907 | 15.1% | 49.7% | 21.9% | 2.27 |
| A7 | `payload_entropy>0.80` ∧ `scrambler_enable=0` ∧ `data_width_bits≥128` | config × **randomization** | +0.26 | `DATA_MISMATCH` | 179 | 3.0% | 45.8% | 25.5% | 1.80 |
| A8 | `power_mode=turbo` ∧ `temperature_c>75` | **telemetry** | +0.25 | `THERMAL_SHUTDOWN` | 589 | 9.8% | 49.4% | 23.6% | 2.10 |

A1 and A2 are the two relationships carried over from the previous synthetic
generator, at the originally specified strengths (85% and +35%).

**Cross-file by design.** A4 and A8 live entirely in `telemetry.csv`; A7 needs
`randomization.csv` joined to `config.csv`. An ingestion layer that fails to join
will silently lose three of eight rules — which is exactly what bundle C is for.

**Failing-run error taxonomy (A):** `TIMEOUT` 348, `DATA_MISMATCH` 328,
`FIFO_OVERFLOW` 294, `ASSERTION_FAIL` 168, `THERMAL_SHUTDOWN` 136,
`ECC_UNCORRECTABLE` 110, `PROTOCOL_VIOLATION` 93, `RETENTION_FAIL` 89.

## 6. Noise population

Failures that no rule claims are assigned a noise tag — `DATA_MISMATCH` /
`ASSERTION_FAIL` in A, `REG_MISMATCH` / `ASSERTION_FAIL` in B — with randomized
addresses and cycle counts. This is the seed-noise population. It should **not**
be attributed to any configuration cause. A root-cause engine that confidently
explains these is overfitting.

Conversely, **A5 and B5 are deterministic RTL bugs**: their error text is
byte-identical on every hit, independent of seed. After fingerprint masking they
must collapse into exactly one tight, high-purity cluster each. That is the
cleanest available check that fingerprinting works.

## 7. Modeling ground rules

**GR-21 — Exclude outcome-coupled telemetry from the risk model.** `telemetry.csv`
legitimately contains post-run resource measurements. They are *consequences* of
the run, not predictors available beforehand, and they leak the label:

> **Leaky — must not be model features:** `wall_time_s`, `cpu_time_s`,
> `peak_mem_mb`, `disk_io_mb`, `sim_perf_cycles_per_sec`, `license_wait_s`,
> `power_w`, `cpu_util_avg_pct`, `cpu_util_peak_pct`, `mem_util_avg_pct`
>
> **Safe — genuine pre-run environment:** `temperature_c`, `voltage_mv`,
> `power_mode`, `host`, `simulator`, `simulator_version`, `cpu_model`,
> `cpu_cores_allocated`, `grid_queue`

Measured with LightGBM, 75/25 split: including the leaky columns inflates test AUC
to **0.925** (A) and **0.861** (B), and `sim_perf_cycles_per_sec` / `wall_time_s`
dominate the importance ranking — a meaningless result for a recommender that must
choose a configuration *before* running it. Excluding them:

| Bundle | Leak-free test AUC | Top drivers recovered |
|---|---|---|
| A | **0.867** | `payload_entropy`, `temperature_c`, `voltage_mv`, `prefetch_depth`, `error_injection_rate` |
| B | **0.835** | `temperature_c`, `voltage_mv`, `payload_entropy`, `rand_wait_states`, `arbitration_scheme` |

Treat ~0.85 as the target. Materially higher usually means leakage; `seed` and
`test_id` must also be excluded (`seed` is pure noise by construction, and a model
that uses it is memorizing).

**GR-22 — Rank features by gain or SHAP, not split count.** Split-count importance
is biased toward high-cardinality continuous columns, which is why the categorical
drivers of A1 (`test_name`, `cache_policy`) rank low on split count despite having
the strongest lift in the dataset. SHAP should surface them.

**GR-23 — Outcomes are the only label source.** `outcomes.status` /
`outcomes.pass_fail` (or the log verdict in legacy mode). Never derive the label
from error counts.

**GR-24 — Throughput for the Pareto plot** comes from `outcomes.throughput_mbps`,
which is a measured per-run value, not an aggregate. Scales differ by an order of
magnitude between bundles (A: NVMe-scale; B: 0.17–231 MB/s, median 12.6), so axes
must be computed from the current dataset, never hardcoded.

**GR-25 — Config diff** should compare passing against failing runs *within the
same* `test_name`/`sequence_name`. A1 and B1 are the intended showcase: hold
`test_name=Back_To_Back_Program` fixed and `cache_policy` is the parameter that
separates the two populations.

## 9. Regenerating and scaling

Deterministic — same seed, same bytes.

```bash
python tools/generate_structured_dataset.py --all
```

Seeds: A 1337, B 2024, C 777, D 4242. To build a 50,000-run corpus (≈420k
transaction rows, ~95 MB log):

```bash
python tools/generate_structured_dataset.py --profile nvme_axi --n-runs 50000 --seed 99 --out-dir data/datasets/dataset_large
```

Re-running a bundle first deletes the artifacts it owns, so a stale file from a
previous run can never be picked up as input.

**These rules describe synthetic data only.** They must not be assumed to hold for
real uploaded datasets, and nothing in the analytics path should hardcode them.
